# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`dl_elevation` scrapes a Digital Elevation Model (DEM) from a WMS server one pixel at a time, one `GetFeatureInfo` request per pixel, into a single-band float32 GeoTIFF, and resumes safely across runs. The default source is the City of Cape Town's public server. `dem2mesh`, the second command, turns an elevation GeoTIFF, such as one of `dl_elevation`'s or the City's 5 m model, into a printable STL solid, a PLY surface and a Blender scene; its section is below. macOS is the primary platform. The headless build is meant to work on Linux as well, but that is untested: it has never been compiled there.

Design and plan: `docs/superpowers/specs/2026-10-04-cli-refactor-design.md` and `docs/superpowers/plans/2026-10-04-cli-refactor.md` for `dl_elevation`; `docs/superpowers/specs/2026-10-19-dem-to-mesh-design.md` and `docs/superpowers/plans/2026-10-19-dem-to-mesh.md` for `dem2mesh`; `docs/superpowers/specs/2026-10-21-simplify-and-tiles-design.md` and `docs/superpowers/plans/2026-10-21-simplify.md` for `--tolerance`, which is Part A of that design, and `docs/superpowers/plans/2026-10-22-footprints-and-tiles.md` for Part B, `--footprint`, `--tile`, `--blocks` and `--min-piece`, which is built.

## Build, test, run

CMake 3.27+ with Ninja. The first configure downloads the pinned dependencies. The first build also compiles Catch2, so allow a few minutes.

```bash
cmake -G Ninja -DCMAKE_BUILD_TYPE=Debug -S . -B build
```

```bash
cmake --build build
```

```bash
ctest --test-dir build --output-on-failure
```

One unit's tests by Catch2 tag, for example `./build/demdl_tests "[downloader]"`. One case by name, for example `./build/demdl_tests "a stop request saves the partial row and goes no further"`.

Options: `-DDL_ELEVATION_PREVIEW=OFF` drops the GLFW window and every OpenGL dependency (default ON on macOS, OFF elsewhere). `-DDL_ELEVATION_TESTS=OFF` skips Catch2.

Homebrew packages: `libtiff libgeotiff openssl@3`, plus `pkg-config` and `glfw` for the preview (and `glew` on Linux, untested). Homebrew's `cpp-httplib` is used when it is 0.46.1 or a later 0.46 release; otherwise FetchContent downloads the pinned version.

Running `dl_elevation` makes real requests to a public server. Check a command line with `--dry-run`, which writes nothing and prints the plan, including a `tls:` line saying how requests would be secured, and never start a live download just to see whether the build works:

```bash
./build/dl_elevation --north -34.1845418 --south -34.2163447 --west 18.4185791 --east 18.4625244 --width 2048 --height 1792 --output "${TMPDIR:-/tmp}/simonstown.tif" --dry-run
```

The `.tif` files in the repository root are old RGB16 downloads that `dl_elevation` refuses to resume; `--overwrite` on them would destroy them, so choose another `--output` for new runs.

The end-to-end tests and the loopback WMS script in the plan's Task 13 Step 9 run the whole program against 127.0.0.1 and need no network. Live requests to the City of Cape Town server are for the owner to start.

`./build/dl_elevation --help` lists every flag. Headless is the default; `--preview` opens the window.

## Layout

- `src/demdl/` is the static library holding `dl_elevation`'s logic, which `demmesh` builds on: `BoundingBox`; `Config` (every option plus `validate()`); `WmsQuery` (URL building and body parsing, pure functions); `RetryPolicy`; `DemRaster` (float32 grid, GeoTIFF I/O, resume checks); `TiffSetup` (libtiff's process-wide setup: the `GDAL_NODATA` tag and a handler that collects libtiff's errors, shared by `DemRaster` and `GeoTiffGrid`); `PixelFetcher` (one-method interface); `ElevationClient` (httplib); `Downloader` (row loop, pool, checkpoints, stop handling); `ProgressSink` with `ConsoleReporter`; `StopToken` (the shared stop flag, which keeps the first reason given).
- `src/mesh/` is the static library `demmesh` behind `dem2mesh`, namespace `demdl::mesh`: `TransverseMercator` (forward projection and the UTM table); `GeoTiffGrid` (a GeoTIFF's geometry, and a pixel window read as float32 with no-data as NaN); `CropWindow` (crop box to pixel window, the window in metres, the `window:` text); `NoDataFill` (nearest-height fill); `Resampler` (quadratic B-spline); `BasePlane` (the base-plane rule); `Predicates` (exact integer orientation and in-circle tests on grid points); `ProfileSimplifier` (the one-dimensional rule that settles a chunk's sides); `PolygonTriangulation` (exact ear clipping of a simple polygon on grid points); `Footprint` (the data mask, the footprint's cells with their closing, enclosed fill and corner joins, and per block the pieces with their outline loops and runs); `Tiles` (the block lattice, block names and the `--blocks` text); `Simplifier` (`simplifyGrid`, the greedy TIN over a lattice of chunks, and `BlockSimplifier`, the same engine block by block over window blocks or a footprint's pieces, into one surface); `SolidMesh` (surface, solid and self-check; `Boundary` and `gridBoundary` give a surface's outline as four sides, `solidFromSurface` builds the solid on any such surface, and `solidMesh` is its wrapper for a grid, which only the tests call); `FootprintSolid` (the solid of a footprint block: wall quads and an ear-clipped base for each piece); `AtomicFileWriter` (little-endian output through `<file>.tmp` and a rename); `StlWriter` and `PlyWriter` (with `stlFileBytes` and `plyFileBytes` for the dry run, and `readBinaryStl` for the tests); `BlenderRunner` (`namedBlender`, `findBlender`, `findOnPath`, `blenderStartProblem`, `runBlender`, which hands the script one STL as `--stl=` or several as `--stl-list=`, a temporary file of their paths).
- `src/mesh/blender_scene.py` is the Python that Blender runs: CMake puts its text into the generated `build/generated/mesh/BlenderScenePy.h` (from `BlenderScenePy.h.in`) as `kBlenderScenePy`, so `dem2mesh` needs no file beside it.
- `src/app/` holds both executables: `Cli.cpp` turns argv into a `Config` with CLI11; `ExitCodes.h` maps a finished run to its exit code; `main.cpp` wires the components and handles signals. `MeshCli.cpp` turns `dem2mesh`'s argv into `MeshOptions` (object library `demmesh_cli`), and `dem2mesh_main.cpp` runs the pipeline as named steps and prints the summary or the dry run's plan. `CliChecks.h` holds the strict value checks both parsers share.
- `src/preview/` holds the optional GLFW/OpenGL sink, `PreviewWindow`, and its `Shader.h`. `Palette.h` there holds the preview's colours and includes no OpenGL header, so its tests build in every configuration.
- `tests/` has one Catch2 file per unit, the doubles `FakeFetcher.h` and `RecordingSink.h`, and the helpers `TempDir.h` and `ExampleConfig.h`. For `dem2mesh` it adds `GeoTiffFixtures.h` (small geographic and Transverse Mercator GeoTIFFs written by the tests), `IslandFixture.h` (the island: 24 x 18 samples of sea, an island with a lake and a channel, an islet, a lone sample and two blobs that touch at a corner, with heights and a box, shared by the footprint, simplifier, solid and end-to-end tests), `SpawnedProcess.h` (runs a built executable as a child, for both end-to-end files) and `FakeBlender.h` (`ScopedEnv` and a shell-script stand-in for Blender, which also takes a list of STLs). Nothing touches the network except an in-process `httplib::Server` on loopback.
- `tests/test_EndToEnd.cpp` spawns the built `dl_elevation` against a loopback WMS, and `tests/test_Dem2MeshEndToEnd.cpp` spawns the built `dem2mesh`, so the test target depends on both executables.
- Test names must not begin with `-`, because ctest passes each name to Catch2 as an argument.

## Behaviours of dl_elevation to keep in mind

- **The raster is the resume state.** NaN means not fetched, or failed last time and due for retry. `-32768`, the declared NoData, means the server's mask band says there is no elevation there (`BAND 1: 0`, as at sea, where `BAND 0` reads 0) and is final; a body without `BAND 0:` is a parse error, retried, never NoData. The mask rule applies to every `--layer`: one whose `BAND 1` is a data band rather than a 0/255 mask would have every pixel where that band reads exactly 0 stored as NoData, so check a captured response before using another layer. On start an existing output must match width, height, bounding box (within 1e-9 degrees) and layer, otherwise exit 1 with the differences; `--overwrite` starts fresh. Files from the old RGB16 format are rejected.
- **What the server returns.** Checked live on 2026-10-05: the server samples the top-left corner of each requested pixel (its `Point:` line says so), and at 2048 x 1792 over the Simon's Town box, about 2 m per pixel, its heights equal the earlier download's exactly. A 4 x 3 test grid over the same box returned different heights at the same corner points, so coarse requests appear to be answered from lower-resolution overviews: use fine grids for real data. The files declare `RasterPixelIsArea`, so GIS shows each height half a pixel south-east of where it was sampled, about 1 m on the default grid and below the model's 5 m resolution.
- **Checkpoints are atomic.** Before anything is written, the output directory is checked and the sink is created. The checkpoint is saved before the first request and after every row with work. Each save writes the whole raster to `<output>.tmp`, syncs it and renames it over the output, so every row with work rewrites 4 x width x height bytes: about 26 GB over a 2048 x 1792 run, and about 50 TB for a square grid near the 2^29-pixel limit, enough to wear an SSD noticeably. A save after the first request that fails, on a full disk for instance, stops the run with exit 2 and the last good checkpoint intact, and is reported on stderr as `error: checkpoint write failed: ...` (after another stop reason, `error: interrupted; checkpoint write failed: ...`) as well as in the summary on stdout. If the save before the first request fails, the run exits 1 with `error: ...` and makes no request.
- **Stopping is one flag.** SIGINT, SIGTERM, SIGHUP (closing the terminal; left ignored when the tool is started under `nohup`), closing the preview, a checkpoint write failure, or the consecutive-failure limit set the `StopToken`. Queued pixels are abandoned, in-flight ones finish, and the partial row is saved. `main` prints `stopping: ...` to stderr.
- **Exit codes:** 0 complete; 1 usage, configuration, file or internal error; 2 stopped early and resumable; 3 finished with failed pixels and resumable. A second Ctrl-C kills the process by SIGINT, which the shell reports as 130, and because Ctrl-C reaches the whole foreground job, a calling shell script stops too. A second SIGTERM kills it by SIGTERM, which the shell reports as 143, and a second SIGHUP by SIGHUP, 129.
- **Failures:** with the default policy and 8 workers, an unreachable server or a wrong path takes about 20 minutes to reach the 100-failure limit (longer when each connection attempt times out). Certificate errors are not retried, so they fail at once. `ca-bundle.crt` in the repository root is Mozilla's CA snapshot of 2019-01-22, root certificates only. The old program passed it to httplib but turned verification off, so it never verified anything. `--ca-bundle` replaces the system trust store entirely rather than adding to it, so that file cannot supply an intermediate certificate the server fails to send, and it breaks chains whose root is newer than 2019. If verification fails, build a PEM file holding the server's intermediate certificate(s) and its root and pass that with `--ca-bundle`; never use `--insecure` for a long run. The first failed request and the first unparseable body are each reported once per run on stderr. Progress lines go to stdout.
- **Threading:** worker threads write distinct raster cells and own one `ElevationClient` each; sinks guard their own state; nothing prints from a signal handler.
- The old single-file `main.cpp` and the `include/` LearnOpenGL boilerplate are gone. Do not resurrect them.

## dem2mesh

`dem2mesh` reads a single-band elevation GeoTIFF and writes three files from one resampled grid, simplified to a TIN when `--tolerance` asks (see **Simplification**), so the print and the renders match; with `--tile` it writes one STL for each block of the window instead of one (see **Footprints and tiles**). `STEM.stl` is a closed solid to slice and print: the terrain on top, upright walls and a flat base. `STEM.ply` is the terrain surface alone; it is what Blender is given, and it opens in any 3D tool. `STEM.blend` is a scene of that surface with a camera, a sun and a material, built and saved by the user's Blender. `dem2mesh` makes no network request. `./build/dem2mesh --help` lists every flag.

Check a command line with `--dry-run` first. The dry run reads the window's pixels, builds and checks the solid, and prints every choice a run would make, down to the file sizes and the Blender it would start. It writes nothing.

```bash
./build/dem2mesh -i ~/Downloads/CCT_GLM2019_5m_DEM_1D_v1_tiles/CCT_GLM2019_5m_DEM_1D_v1_r3_c1.tif -o "${TMPDIR:-/tmp}/r3c1" --grid 400 --scale 0.02 --dry-run
```

Without `--dry-run`, that command writes `r3c1.stl`, `r3c1.ply` and `r3c1.blend` in about 11 s with the Debug build: the whole tile, 32.3 x 19.7 km, as a model of 645.5 x 393.9 x 23.8 mm. Table Mountain is a crop of the same tile:

```bash
./build/dem2mesh -i ~/Downloads/CCT_GLM2019_5m_DEM_1D_v1_tiles/CCT_GLM2019_5m_DEM_1D_v1_r3_c1.tif -o "${TMPDIR:-/tmp}/table-mountain" --north -33.9459 --south -33.9800 --east 18.4300 --west 18.3900 --grid 500 --scale 0.02
```

It makes a print of 74.5 x 76.1 x 21.9 mm and 511,004 triangles in about 10.5 s, 8 s of them in Blender. The examples write to `$TMPDIR`. Claude writes models only under `$TMPDIR`, the session scratch directory or a directory the user names; `~/Downloads` holds the City's input files and gets no outputs.

- **Checks and exit codes.** Options are checked first, with the strict number checks of `dl_elevation`'s parser. Then the input must be a readable regular file, the output directory writable and, without `--overwrite`, none of `STEM.stl`, `STEM.ply` and `STEM.blend` present (with `--tile`, none of the lattice's block files, `STEM.ply` and `STEM.blend`; the lattice comes from the grid, so that check waits for the file's header and is still made before any pixel is read). Then, unless `--no-blend` was given, a Blender named by `--blender` or `$BLENDER` must be an executable file, or the run stops with the flag or variable named (see **Blender**). A dry run makes the same checks, all before the input is opened but that one. Exit 0 from a run that is not a dry run means that the STL (every written block's, with `--tile`) and the PLY were written and, unless `--no-blend` was given, the `.blend` too, with Blender's check passed. `--dry-run` and `--help` exit 0 having written nothing. Every failure is exit 1 with an `error: ...` line on stderr.
- **Inputs.** It reads single-band float32, float64, int16, int32 or uint16 GeoTIFFs, in strips or tiles, north up, either geographic in degrees or Transverse Mercator in metres. A projected file must give its Transverse Mercator parameters as GeoKeys or be a WGS 84 UTM zone by EPSG code (32601 to 32660, 32701 to 32760); there is no PROJ and no other EPSG table. Refused, with the file named: other band counts and sample types, the old RGB16 downloads among them; rotated, sheared, mirrored or upside-down files; other projections; the south-oriented Lo grids (EPSG 2046 to 2055, or `CT_TransvMercator_SouthOriented`); other EPSG codes without parameters; units other than metres and degrees. The projection, orientation, length and angle refusals end `reproject it first, for example with gdalwarp`, and heights in another unit `convert them to metres first`. No-data is `GDAL_NODATA` when the file has it, plus any NaN or infinite value. Heights are taken as metres above sea level, whatever the vertical datum.
- **Where the samples sit.** `RasterPixelIsPoint` samples sit on the pixel positions and `RasterPixelIsArea` ones at the pixel centres. A file that `dl_elevation` wrote (its `ImageDescription` starts `dl_elevation;`) declares area, but its samples stay on the pixels' north-west corners, where the server measured them (see "What the server returns"). The mesh runs from the window's first sample to its last. A crop's window is the smallest block of whole samples covering the box, so it is slightly larger, and a crop that overlaps the file by fewer than 2 x 2 samples is refused.
- **The City's model.** `~/Downloads/CCT_GLM2019_5m_DEM_1D_v1.tif` (1 GB, 12912 x 19696 samples) and its ten tiles in `~/Downloads/CCT_GLM2019_5m_DEM_1D_v1_tiles/` are float32 at 5 m, Transverse Mercator Lo19 (central meridian 19, scale 1, no false origin, GRS 80), `RasterPixelIsPoint`, with `GDAL_NODATA` 0. The whole file's heights run from -37.9 to 1590.1 m. No-data, the sea and the land outside the municipal boundary, covers 154,573,967 of its 254,314,752 pixels. Its dry run at `--grid 400` took 67 s in the Debug build, 36 s of them in the fill, with a 1 GB memory footprint. These files are inputs only.
- **No data.** Before resampling, each no-data pixel takes the height of the nearest pixel that has one. So the sea comes out flat at about coast level, land beyond a data boundary continues as a plateau at the edge's height instead of ending in a cliff, and a gap in an unfinished `dl_elevation` file takes its surroundings' height instead of becoming a pit. Nearest is counted in steps up, down, left and right, and a tie goes to the first pixel in scan order, the northmost and then the westmost. So beyond a diagonal data boundary the fill copies heights straight down the columns where the blank lies south of the data, and along the rows where it lies north, not square to the edge; only made-up ground is affected. A window with no height at all is an error. The `heights:` line counts the filled pixels and gives the range they were given: -0.96 to 1576.5 m on the City's whole file.
- **Resampling.** Every run resamples, full resolution included, with a separable quadratic B-spline of three taps at the source spacing, which never leaves the source's range. On a coarser grid the kernel stretches to the output spacing, so each vertex averages the samples under it: antialiasing and smoothing in one pass. A B-spline approximates, so a sharp summit comes out a little lower, more so on a coarse grid. The `summit:` line gives the height before and after: the tile's 1084.7 m becomes 1084.33 m in the Table Mountain mesh at `--grid 500` and 1075.2 m in the whole tile's at `--grid 400`. The mesh's outermost rows and columns come from the window's edge samples alone, smoothed along the edge but not across it, and its corners are the corner samples exactly. `--grid W` without `xH` takes the height from the window's aspect, so that cells come out square; each side must be at least 2.
- **Simplification.** `--tolerance T` writes a triangulated irregular network (TIN) in place of the resampled grid's triangles, so that flat ground, the sea above all, costs a few big triangles and detail stays where the terrain has it. T is in model units, after `--z-scale` and `--scale`, above 0, with no default: without the flag the output is the full grid, byte for byte as before, but in **Footprints and tiles**' modes, which simplify at 0 without it. `--tolerance 0.05 --scale 0.02` is 0.05 mm on a 1:50,000 print and 2.5 m of terrain, the value planned for printing the City; the simplifier is given T / (`--z-scale` x `--scale`) metres. The guarantees: every vertex is a grid sample at its exact height; the four corners are vertices, and the window's sides are made of the boundary's vertices alone, so that the surface never leaves the rectangle; at every grid sample the surface is at most T above or below it; the triangles make one sheet over the window, counter-clockwise seen from above, with no overlap, no gap and no unused vertex; and the same grid and tolerance give the same triangles on every run. The fewest triangles is not promised. Before the solid is built, on both paths, the run counts the surface triangles that do not face up (`downwardFacingTriangles`), by the sign of each normal's z worked in double from the float coordinates the files carry, and a count above 0 stops it with nothing written and `error: mesh self-check failed: N surface triangles face down or have no area`, a bug and not a fault of the input, which the solid's own check and Blender's, seeing edges and the total volume, would not catch when float rounding turns a triangle over. The error is measured on the grid's heights, before the lift to the base level, which `chooseBasePlane` never lets act because it puts that level at or below the window's lowest height. The grid is cut into chunks of 2048 x 2048 cells from the north-west corner, the last ones cut short. Each chunk's four sides are simplified first, on their own, by Douglas and Peucker's rule on the vertical distance; greedy insertion then fills the interior, the sample furthest from the surface going in next (the smallest row and then the smallest column on a tie) until none is further than T, with the triangulation kept Delaunay by exact integer tests and no epsilon. Chunks that share a side keep the same vertices on it, so their surfaces join into one sheet; the seams cost a few triangles that one triangulation of the whole grid might not need, so a plane gives two triangles per chunk, not two in all. The PLY, and so the Blender scene, carry the TIN with the same planar `s` and `t`.
- **Simplified output and limits.** With `--tolerance` the summary gains a line after `grid:`, here for the Table Mountain crop at `--grid 500 --scale 0.02 --tolerance 0.05`: `simplify: tolerance 0.05 units (2.5 m), 255500 grid vertices to 21985, 508980 triangles to 43649`. It gives the tolerance as given and in metres to the centimetre, then the grid's vertices and triangles against the TIN's, all plain integers. `solid:` counts the simplified solid. `summit:` gives the TIN's highest vertex, which the tolerance can leave below the grid's summit: 1083.33 m in the mesh against the grid's 1084.33 m for that crop. The dry run simplifies too, so its counts and sizes are exact, and a whole-City dry run costs as much as the run minus the writing: about 26 s either way in a Release build. Without `--tolerance` the grid is limited to 25,000,000 vertices, as before: it is what is written, or in **Footprints and tiles**' modes what is simplified at 0, which keeps nearly every sample (see **Block limits and refusals**). With it the grid is only simplified and may have up to 2,147,483,647 vertices, in every mode, refused before any pixel is read above that: `error: the output grid is 2500000000 vertices; with --tolerance the limit is 2147483647: use --grid or crop`. The 4,000,000-vertex warning and the 25,000,000 limit then count what is written, the simplified mesh: the warning once it has been simplified, the limit while it is simplified as well (below). The warning reads as before but for its start: `warning: the simplified mesh is 7104603 vertices: the STL will take 710 MB, the PLY 327 MB, and Blender about 9.8 GB of memory (--no-blend skips it)`, which the r3_c1 tile at full resolution gives for `--tolerance 0.05` at `--scale 1`, a tolerance of 0.05 m. A simplified mesh above 25,000,000 vertices is refused before the solid is built and with nothing written. The simplifier is given the limit and stops the mesh while making it, so that a tolerance near 0 cannot build gigabytes first: a chunk, or a block in **Footprints and tiles**' modes, is stopped as soon as the surface before it, plus the vertices it has taken, exceeds the limit plus the samples round its edge, a slack for the vertices it shares with the chunks or blocks before it, with `error: the simplified mesh is more than 25000000 vertices; the limit is 25000000: raise --tolerance, or use --grid or crop`. One that ends above the limit by less than that slack is refused once it is made, with `error: the simplified mesh is N vertices; the limit is 25000000: raise --tolerance, or use --grid or crop`. No mesh that ends within the limit is stopped, so every such run writes what it wrote before the limit was given to the simplifier. The dry run's plan has a `memory:` line between `grid:` and `simplify:`, `memory: window 568452 samples and grid 255500 vertices, 4 bytes each: about 3 MB`, for the window and the grid, each float32 and held together while the one is resampled into the other. The sum is to the nearest MB, or from 1,000 MB up in GB to one decimal. It counts the window and the grid only, and with `--footprint data` the window's data mask too, a byte a sample, held beside them while the one is resampled into the other: `memory: window 25436640 samples and grid 25436640 vertices, 4 bytes each, and the data mask, a byte a sample: about 229 MB` for r3_c1 with the puzzle's flags, and about 2.3 GB for the City's puzzle, which peaked at 2.29 GB. It matched the City (about 2.0 GB, measured 2.04 GB), but the fill's work lists and a large TIN come on top: the 7,104,603-vertex run above reads about 203 MB and peaked at 873 MB in a Release dry run.
- **Simplification measured.** All at `--tolerance 0.05 --scale 0.02`, which is 2.5 m. The Table Mountain crop at `--grid 500` keeps 21,985 of 255,500 vertices and writes 43,974 triangles and an STL of 2,198,784 bytes, against 511,004 triangles and 25,550,284 bytes without the flag, in 0.7 s without Blender in the Debug build; read back, the STL is within 2.499963 m of all 255,500 grid samples at the vertices' exact positions, and 2.500029 m with the STL's float32 positions (29 micrometres of terrain, 0.6 nm on the print); the tile at `--grid 400` reads back 2.498607 m either way. The whole r3_c1 tile at `--grid 400` writes 19,348 triangles against 195,204, in 3.8 s without Blender: `simplify: tolerance 0.05 units (2.5 m), 97600 grid vertices to 9672, 193914 triangles to 19142`. Its sea costs 61 triangles: that many of the TIN's 19,142 top triangles lie over no-data (the sea and the land outside the City, 32% of the window), where the grid had 62,040 of 193,914. At full resolution that tile is 25,436,640 grid vertices to 117,603 and an STL of 11,760,584 bytes, with a dry run of 2.4 s in Release that reads `about 203 MB`. The whole City at full resolution, with Blender left out (`--no-blend`), took 26.2 s in a Release build (32.4 s with the file not yet in the cache; 16 s of the 26.2 s are the simplification) and peaked at about 2.04 GB of memory: `simplify: tolerance 0.05 units (2.5 m), 254314752 grid vertices to 1023872, 508564290 triangles to 2047073`, a solid of 2,047,748 triangles, an STL of 102,387,484 bytes and a PLY of 47,089,628; read back, no top triangle faces down. Blender was not run on it; the dry run estimates about 1.6 GB for it. Run it from a Release tree, which `build*/` already ignores: `cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -DDL_ELEVATION_TESTS=OFF -S . -B build-release`, then `cmake --build build-release`, then `./build-release/dem2mesh -i ~/Downloads/CCT_GLM2019_5m_DEM_1D_v1.tif -o "${TMPDIR:-/tmp}/cape-town" --scale 0.02 --tolerance 0.05 --no-blend`. The fill alone takes 36 s in Debug (see **The City's model**) and 4 s in Release; the Debug build was not timed on the whole run. Float32 storage can put the error read back from the STL a little over T: the City's largest is 2.500020 m with the heights as stored, and 2.524 m with the vertices' float32 positions too, on one cliff of filled no-data; the simplifier itself is exact. Two edges are known. A grid much wider than the window's aspect, few rows and many columns, makes the resampler hold every source row at the output's width: `--grid 50000x2` on r3_c1 peaks at 0.9 GB while `memory:` says about 102 MB, and `--grid 1000000x2` needs about 16 GB, with or without `--tolerance`; `--tolerance` lets the long side reach 1,073,741,823, terabytes. Nothing refuses it yet. And very small values print as zero: a window and grid under half a megabyte read `about 0 MB`, and a tolerance under 5 mm of terrain reads `(0 m)`, though the simplifier is given the exact value.
- **Footprints and tiles.** The puzzle command is `./build-release/dem2mesh -i ~/Downloads/CCT_GLM2019_5m_DEM_1D_v1.tif -o "${TMPDIR:-/tmp}/cape-town" --scale 0.02 --tolerance 0.05 --footprint data --tile 100` (see **The City as a puzzle**). `--footprint window|data` (default `window`) puts the solid over the whole window, as before, or only where the DEM has data (see **The footprint**). `--tile SIZE` splits the window into square blocks of SIZE model units, each a closed solid of its own written as `STEM_rRR_cCC.stl`, numbered from the north-west from 1 and zero-padded to the digits the counts need (`cape-town_r03_c05.stl`); a block is `round(SIZE / (scale x cell))` cells a side, counted from the north-west corner, so the City at 1:50,000 is 13 x 20 blocks of 1000 x 1000 cells, the last ones cut short. `--blocks ROWS:COLS` writes only those blocks, each part a number or a range from 1 (`3-5:2-4`, `7:12`; leading zeros are accepted, `03:05`), and needs `--tile`; the others are listed. `--min-piece A` (default 1) drops a piece smaller than A square model units, and needs `--footprint data`: without it the run stops with `error: --min-piece requires --footprint data`. Each block's STL is in its own frame, x and y from the block's south-west corner, z as everywhere. One base plane, chosen from the whole window's data heights, serves every block, so they sit flush. A block's side is simplified once, run by run, the runs split at the outline's turns and, on a block side, wherever the cell across it changes; the block beyond gets the same samples, so the two share vertices and meet without a step. `STEM.ply` and `STEM.blend` hold the whole area (the selected blocks, with `--blocks`), and Blender checks every block written (see **Blender's STL check**). Without `--tile`, `--footprint data` is one block and writes `STEM.stl`; `--tile` with `--footprint window` gives full squares, with the fill where the sea was. `--tile` or `--footprint data` without `--tolerance` simplifies at 0, which keeps every sample off its neighbours' plane, and prints `simplify: tolerance 0 units (0 m), ...`; its grid keeps the 25,000,000-vertex cap of a run without the flag (see **Block limits and refusals**). The dry run does everything but write and start Blender, so the City's costs 45 to 58 s in two Release runs, and 2.29 GB, against the `memory:` line's about 2.3 GB for the window, the grid and the data mask.
- **The footprint.** It is worked out once, on the output grid and for every block, from the window's no-data as it was before the fill, carried to the grid by the nearest sample. A cell, the square between four vertices, is in when all four have data. The cells are then closed with a 3 x 3 neighbourhood, so a no-data slit one sample (two cells) wide is filled and one two samples wide stays cut; the grid's edge counts as in for the erosion, so a strip of no-data one cell deep along the window's edge becomes footprint, with filled heights. No-data enclosed by footprint is filled and stays inside (a vlei, a dam, and with a crop a bay whose mouth lies outside it); no-data connected to the grid's edge is cut. A corner contact, a vertex whose four cells are a diagonal pair in and a pair out, is joined: the north-west-most of the two empty cells is added, filled like an enclosed hole, because two shells would otherwise stand walls on one vertical line, which an STL reader that merges corners reads as one edge in four faces, non-manifold to Blender's check (a 5 m cell is 0.1 mm on the print). A piece is a 4-connected set of cells within a block, so one that crosses a block side is a piece of each block; it is dropped under `--min-piece`, and a block with no piece is skipped. The outline runs along grid lines through real samples, up to one cell (5 m) inside the data's edge. A block is the surface over its pieces, a wall of two triangles under every outline edge and a base cut by ear clipping, one closed shell for each piece. `--footprint data` on a file without no-data is one piece, the window: its PLY is byte for byte the `--footprint window` one when both get the same `--tolerance` and the window is up to 2048 cells a side, or when both are tiled; its walls and base are the footprint's, so its STL differs.
- **Block limits and refusals.** Before any pixel is read, with nothing on stdout (a dry run has printed `dry run` by the time the grid is known): a lattice of more than 10,000 blocks, `error: the lattice is 2545240 blocks; the limit is 10000: use a larger --tile`; a block side above 16,384 cells, `error: a block would be 19695 cells tall, but a block side may be at most 16384 cells: use a smaller --tile or a coarser --grid`, and so a footprint without `--tile` above that, `error: the window is 12911 x 19695 cells; a footprint without --tile is limited to 16384 a side: use --tile or --grid`; `--blocks` beyond the lattice, `error: --blocks: '21:1' reaches beyond the lattice of 20 rows and 13 columns of blocks`, not `ROWS:COLS`, `error: --blocks: must be ROWS:COLS, each part a whole number from 1 or a range such as 3-5, not '3-5'`, or without `--tile`, `error: --blocks requires --tile`; and, without `--overwrite`, any block file of the lattice that exists, `error: <stem>_r01_c02.stl exists; use --overwrite`, whether or not this run would write it, since which blocks have land is known only after reading. Without `--tolerance` the grid is refused above 25,000,000 vertices before any pixel is read, as on today's path, since simplified at 0 it keeps nearly every sample, and the refusal names the flag that lifts it: the r3_c1 tile at full resolution with `--scale 0.02 --footprint data --tile 100` gives `error: the output grid is 25436640 vertices; without --tolerance the limit is 25000000: give --tolerance, or use --grid or crop`. With `--tolerance` the grid may have up to 2,147,483,647 vertices, as without blocks, and the simplified mesh is held to 25,000,000 (see **Simplified output and limits**). Every block is simplified before any STL is written, so the simplified mesh's refusal and the 4,000,000 warning, which count the whole-area surface, come before anything is written; the warning reads `warning: the simplified mesh is 10298601 vertices: the STLs will take 1038 MB and the PLY 474 MB` for that tile with `--scale 0.02 --footprint data --tile 100 --grid 5000 --no-blend` and no `--tolerance`, which a dry run reports in 71 s in a Release build. A run with no block to write is an error, after the first pass and before anything is written: `error: no selected block has land to write: no cell has data at all four of its corners`, or `... 24 pieces were dropped under --min-piece 100000`, and without `--tile` `error: the footprint has nothing to write: 1 piece was dropped under --min-piece 100000000`. The block files of the stem that a run leaves behind are left alone and named in `stale:`, in name order: every regular file in the output directory called `STEM_r<digits>_c<digits>.stl`, whatever the padding, that the run does not write (would write, in a dry run), such as the file of a selected block that now has no land and those of another lattice, whose names a change of `--tile`, `--grid`, `--scale` or crop changes; the files of blocks of the lattice outside `--blocks` are not named. Re-making a few blocks of a finished puzzle with `--blocks` into the same stem needs `--overwrite`, which replaces the whole-area `STEM.ply` and `STEM.blend` with the selection's, so give a batch its own `-o` stem or directory.
- **The City as a puzzle.** Run it from a Release tree, as for **Simplification measured** (`cmake --build build-release`): the r3_c1 tile took 28 s in the Debug build against 4.8 s in Release, to the same bytes, and the City was not timed in Debug. The puzzle command took 99.6 s with Blender and a maximum resident set of 2.29 GB (`/usr/bin/time -l`), on a machine whose load average was 9 with another job running, and 48 s with `--no-blend`, which wrote the same 146 STLs and PLY byte for byte. The stages, from `--verbose`: read 10.9 s, fill 11.0 s, resample 5.5 s, footprint 7.1 s, simplify 18.0 s, blocks 3.9 s, write PLY 0.5 s, blender 41.1 s. `simplify: tolerance 0.05 units (2.5 m), 254314752 grid vertices to 662226, 508564290 triangles to 1257162` is the whole-area surface, which the PLY (29.6 MB) and the `.blend` (46.5 MB) hold. 146 of the 260 blocks have land and are written, 114 are skipped, and 32 blocks, written or not, are cut short; there is `corner contacts: 1` and no `dropped pieces:`. The STLs run from 14,084 bytes (r02 c06) to 4,001,184 (r14 c13, 80,022 triangles), 74,628,664 in all, and Blender's check passes on every one: `stl check: 146 files, 1492328 triangles, 0 non-manifold edges, 0 inverted faces`. A scratch script that read the STLs back, undid the frames and compared every pair of neighbouring blocks found 5,853 vertices along the 243 pairs that share a side, identical in x, y and z. The design guessed 50 to 100 MB for a printing service's upload limit; the largest block is 4.0 MB, and the owner checks the service's actual figure against it.
- **Base, plinth and units.** The base plane is at sea level, or at `--base` metres, lowered to the window's lowest height when that lies below it, and then a margin lower: 1 percent of the window's height range, at least 1 m. `--z-scale` multiplies every height and the base; `--scale` then multiplies x, y and z. After scaling, the base goes further down where needed so that the solid is at least `--plinth` units thick (default 2) under its lowest point: for the whole tile at `--scale 0.02`, from -25.49 m to -114.5 m. The `base:` line gives the plane and the reason: `sea level minus a <m> m margin`, `the requested <level> m minus a <m> m margin` or `lowered to the lowest point, <lowest> m, minus a <m> m margin`, each followed by `, then pushed down for a <plinth>-unit plinth` when the plinth acts. The mesh is in metres times `--scale`, with the window's south-west corner at the origin, x east, y north and z up from sea level. An STL carries no unit and slicers read it as millimetres, so `--scale 0.02` makes a 10 km window 200 mm wide; the default `--scale 1` gives metres.
- **Size and memory.** Without `--tolerance`, above 4,000,000 vertices the run warns on stderr with the files' sizes and the memory Blender will need, and goes on: `warning: the output grid is 4002000 vertices: the STL will take 400 MB, the PLY 184 MB, and Blender about 5.6 GB of memory (--no-blend skips it)`. With `--no-blend` the line ends at the PLY: `the STL will take 400 MB and the PLY 184 MB`. Above 25,000,000, an STL of about 2.5 GB, it is refused before any pixel is read: the City's whole file at full resolution gives `error: the output grid is 254314752 vertices; the limit is 25000000: use --grid or crop`. In **Footprints and tiles**' modes without `--tolerance` that refusal is the grid's as well, worded `without --tolerance the limit is 25000000: give --tolerance, or use --grid or crop`, but the warning counts the surface they simplify at 0, after simplifying. With `--tolerance` the grid is simplified rather than written, and both limits move to the simplified mesh (see **Simplified output and limits**). Above 10,000,000 triangles the self-check leaves out its edge check, and a `check:` line says so. The window is held once as float32, 1 GB for the City's whole file, until it has been resampled into the output grid. The surface and the solid, which starts with a copy of it, are then held together until the PLY is written: about 1.8 GB at the 25,000,000-vertex limit. The solid is freed once the STL is written, before Blender starts. Blender's peak resident memory grows at about 0.67 KB per triangle over a floor of about 0.25 GB (583 MB at 511,004 triangles, 1.6 GB at 2,042,004 with Blender 4.5.12): about 5.6 GB at the 4,000,000-vertex warning and about 34 GB at the 25,000,000 cap, more than the owner's 16 GB machine has, so large grids take `--no-blend`.
- **Blender.** It must be 4.2 LTS or later; the script refuses older ones with a message. The owner has 4.5.12 LTS, the Intel build. `dem2mesh` looks for it in this order: `--blender PATH`, `$BLENDER` when set and not empty, `/Applications/Blender.app/Contents/MacOS/Blender` when it exists, then the first `blender` on `PATH`. The first two are used as given, with no fallback, and are checked before anything is read: `--blender ""` is a usage error, and a flag or variable that does not name an executable file exits 1 at once with `error: --blender <path>: does not exist` (or `BLENDER=<path>: ...`, or `is not a regular file`, `is not executable`, `not found on PATH` for a name without a `/`, or for an `.app` directory `is the app bundle; its executable is <path>/Contents/MacOS/Blender`). After writing the STL and PLY (with `--tile`, every block's STL and then the PLY), `dem2mesh` first removes an existing `STEM.blend`, which can be there only under `--overwrite`, so that a Blender that fails or is not found leaves no old scene, and then runs `<blender> --background --factory-startup --python <script> -- <job>`: no window opens, and Blender's output is captured. Blender's start-up alone takes about 6 s on the owner's machine. With no Blender found, the run keeps the STL and PLY and exits 1 with `error: Blender not found: pass --blender, set BLENDER, or install it at /Applications/Blender.app`. `--no-blend` skips Blender and exits 0. A Blender that exits non-zero, or exits 0 without the `stl check:` line or the `.blend`, fails the run, and its output follows the error on stderr. The dry run names the Blender a run would start and about how much memory it will need, `(will be run; about 0.6 GB of memory)` for Table Mountain, 0.3 GB with `--tolerance 0.05`, 1.2 GB for the City's puzzle (with `--tile` the figure adds up every block's triangles, which over-states the peak, since Blender imports one block at a time), or says that none was found, and exits 0 either way.
- **The scene.** It holds the surface from the PLY, not the solid, as an object named after the stem, shaded smooth and left at the PLY's coordinates, with its origin under the middle of the window at its lowest height. A 50 mm camera looks at it from the south-east, 35 degrees up, as close as it can with all of it in frame and 5 percent to spare, and every 3D viewport looks through the camera, so the file opens on the terrain. A sun of strength 3 shines from the north-west, 40 degrees up. The material `Terrain` is a warm grey of roughness 0.9. The world is 0.8 grey to the camera but lights the terrain at 0.25, through a Light Path "Is Camera Ray" mix, so that the sun's shadows read. The render is EEVEE, 1920 x 1080, 64 samples. The `.blend` is saved Zstandard-compressed, and saving over one leaves no `.blend1`.
- **Aerial photos and units.** The material's Image Texture node `AerialPhoto` is wired to nothing, and the PLY's `s` and `t` (x over the window's width, y over its height) arrive as the UV map `UVMap`: draping a photo of the window means loading it into that node and connecting its colour to the shader, with no change to the mesh. The scene is metric. Below `--scale 0.1`, a print, a unit shows as 1 mm (`scale_length` 0.001), the size the slicer prints. At `--scale 1` a unit is a metre. Any other scale shows a unit as the 1/`--scale` metres of terrain it stands for (`scale_length` 1/`--scale`), so 10 m at `--scale 0.1`.
- **Blender's STL check.** After saving, Blender imports the STL into an empty scene and prints `stl check: N triangles, M non-manifold edges, K inverted faces`, which `dem2mesh` repeats as its last line. The check, and the run with it, fails when M or K is not 0, when `mesh.validate()` mends anything, or when the triangle count the STL declares differs from what Blender imported, since its reader drops repeated and degenerate triangles with only a warning. A count mismatch adds `stl check: file declares D triangles, Blender imported N` first. With `--tile` the script is given the list file in place of the STL and checks each block's STL in turn, each in an empty scene of its own so that only one is in memory, within the one session; it prints a single line of totals, `stl check: 146 files, 1492328 triangles, 0 non-manifold edges, 0 inverted faces`, which `dem2mesh` repeats as its last. At the first block that fails it stops, without opening the rest, and prints `stl check: <path> failed` and then that block's own lines, the count mismatch first when there is one; the run exits 1 with that output after the error. The `.blend` is saved before the checks, so a failing block leaves the scene on disk, as a failing STL does. `--verbose` shows a `blender: imported <stl> ...` line for each block it opens (see **The script**). A single STL, tiled or not, is checked in the plain form. It is a second opinion: `dem2mesh` checks the solid itself before writing anything, and a failure there is a bug, `error: mesh self-check failed: ...`.
- **The script.** It is `src/mesh/blender_scene.py`, embedded at build time, so an edit takes effect only after `cmake --build build` (see CMake notes). Each run writes it to `$TMPDIR/dem2mesh-XXXXXX.py` and, for two or more STLs, their absolute paths, one to a line, to `$TMPDIR/dem2mesh-stls-XXXXXX.txt`, and removes both afterwards, however Blender ends; a path with a newline in it would be read as two, so Blender would fail on it, loudly. `--verbose` prints Blender's whole output: the script's `blender:` line per step, among them `blender: checking 146 STL files, one after another` and a `blender: imported <stl> into an empty scene; mesh.validate() found nothing to mend` line for each block, then Blender's own lines, a `Timer 'STL Import' took 3.04 ms` among them for each block, then a `time: blender` line.
- **Interruptions.** `dem2mesh` installs no signal handler. Ctrl-C during a write leaves `STEM.stl.tmp` or `STEM.ply.tmp` (a block's is `STEM_rRR_cCC.stl.tmp`), which a later run replaces, and during the Blender stage it leaves the script in `$TMPDIR`, and with `--tile` the list of STLs, `dem2mesh-stls-XXXXXX.txt`, beside it. The PLY is written before the STL, each renamed into place on its own, so with `--overwrite` an STL write that fails after the PLY's (a full disk, say) leaves the new PLY beside the old STL, and the run exits 1; run it again. A run in **Footprints and tiles**' modes writes the other way round, every block's STL in lattice order and then the PLY, so a write that fails part-way leaves the new blocks before it beside the old ones and the old PLY, and the run exits 1; run it again. The renames come without the sync that `dl_elevation`'s checkpoint makes, so a power cut just after a run can leave a short file.
- **Output lines.** The summary on stdout is one line each of `input:`, `crop:` when one was given, `window:`, `grid:`, `simplify:` when `--tolerance` was given (and in **Footprints and tiles**' modes, which set it to 0 without it), `heights:`, `summit:`, `base:`, `solid:` and `check:` when the edge check was left out, then `wrote:` for the STL and the PLY (see **Puzzle output lines** for a tiled run's), then `blender: <path>`, `wrote: STEM.blend` and `stl check: ...` (or `blender: skipped (--no-blend)`, or `blender: not found` before the error). `input:` ends with `degrees` for a geographic file and with `m` for a Transverse Mercator one, whose window is given in projected metres; the run and the dry run echo a crop in degrees. `--verbose` adds a `time: <stage> <seconds> s` line per stage, `simplify` in place of `surface` with `--tolerance`, and `blocks` in place of `solid`, `check` and `write STL` in **Footprints and tiles**' modes. In the dry run's plan `memory:` and then `simplify:` follow `grid:` when `--tolerance` was given, and in **Footprints and tiles**' modes, which simplify at 0 without it. The dry run prints `dry run` after the checks and before it opens the input, so a dry run that fails later, on a crop beside the file for instance, shows that line alone on stdout and the error on stderr, and exits 1; one that fails a check, a bad `--blender` for instance, prints nothing on stdout.
- **Puzzle output lines.** After `base:` the summary of a tiled run has, in this order: `tiles: 13 x 20 blocks of 1000 x 1000 cells (5000 x 5000 m, 100 x 100 units); 146 with land, 114 without, 32 cut short at the east or south edge`, which counts the whole lattice, selected or not, "with land" meaning a kept piece; a line for each block written, `block r14 c13: 74% land, 80022 triangles, 4.0 MB, cape-town_r14_c13.stl` (the share of the block's cells its kept pieces cover, `0%` for a tiny piece, its solid's triangles, its file and its size in megabytes); `skipped: no land in r01 c01, r01 c05, r01 c06, ...` for the selected blocks with no piece; `not selected: r1 c1, r1 c2, r1 c3, ...` for the blocks outside `--blocks` (the r3_c1 tile with `--blocks 4:2-3`), so every block is written, skipped or not selected, once; `dropped pieces: r4 c1 520 cells 5.2 units2` (the r3_c1 tile with `--min-piece 20`), each piece under `--min-piece` in a selected block, by block when there are tiles, in cells and square model units; `corner contacts: 1`, when above 0, the contacts joined inside the blocks written, even one whose piece `--min-piece` then drops, so a join on a block side is counted by none; and `stale: r3c1_r2_c2.stl, r3c1_r2_c3.stl, r3c1_r4_c1.stl` (the r3_c1 tile, written once, then again with `--overwrite --min-piece 3000`), every block file of the stem that the run leaves behind, of this lattice or another (see **Block limits and refusals**). Without `--tile` those give way to `footprint: 84% of the window, 1 piece` (the Table Mountain crop widened to `--west 18.36`, with `--footprint data --tolerance 0.05 --scale 0.02` and no `--grid`, which reaches the sea), then `dropped pieces:`, each piece with no block label, `corner contacts:` and `stale:`, which names every block file of the stem, since `STEM.stl` is no block's. Then `solid: 1492328 triangles, STL 74628664 bytes, PLY 29587864 bytes` totals the blocks, and `wrote:` names every STL in lattice order and then the PLY. The dry run's plan has `would write:` in their place and `output:` lines for the PLY and the `.blend` only; without `--tile` it has no `would write:` and the usual `output:` lines for the STL, the PLY and the `.blend`. `--verbose` adds `time: footprint`, with `--footprint data`, and `time: blocks`.
- **Tests.** The tags are `[clichecks]`, `[tm]`, `[geotiff]`, `[crop]`, `[fill]`, `[resample]`, `[baseplane]`, `[predicates]`, `[profile]`, `[polygon]`, `[footprint]`, `[tiles]`, `[simplify]`, `[solid]`, `[footsolid]`, `[writers]`, `[meshcli]`, `[blender]`, `[mesh-e2e]` and `[slow]`. `[mesh-e2e]` spawns the built `dem2mesh` on small GeoTIFFs that the tests write, among them the island for the footprint and tile cases, and most of its Blender cases run the shell script of `tests/FakeBlender.h` instead. Four cases run the real Blender when `findBlender` finds one, and skip with `Blender not installed` otherwise: in `[mesh-e2e]` a run's check of one STL and the check of every block of a tiled run, in `[blender]` the units case and the list case; the case for a missing Blender skips where the app is installed. Those four carry `[slow]` too: they start Blender eight times and take about 79 s of the suite's 200 s, and `./build/demdl_tests "~[slow]"` skips them for the inner loop. `ScopedEnv` in `tests/FakeBlender.h` sets or unsets an environment variable for one test and puts it back; child processes see the change. ## CMake notes

- Link `httplib::httplib`, never bare `httplib`. Only the namespaced target exists when Homebrew's package is found, and the bare name silently drops `CPPHTTPLIB_OPENSSL_SUPPORT`.
- `CMAKE_FIND_FRAMEWORK` is `LAST` because `/Library/Frameworks/Mono.framework/Headers` ships a libtiff 4.0.9 `tiff.h` that otherwise wins over Homebrew's.
- Apple clang searches `/usr/local/include` ahead of every `-isystem` directory, so it compiles `/usr/local/include/httplib.h` even when FetchContent supplies the pinned copy. After `brew upgrade cpp-httplib` moves past 0.46, the build silently compiles the newer header. Pin the formula with `brew pin cpp-httplib`, or bump the pin in `CMakeLists.txt` to match.
- Policy CMP0156 is set to NEW so that `libdemdl.a` is linked once when a target names both `demdl` and `demdl_cli`, which links `demdl` itself. Without it, the Xcode 15 linker warns about a duplicate library. The block is guarded by `if(POLICY CMP0156)` because the minimum version, CMake 3.27, predates the policy, which arrived in 3.29. `dem2mesh` and the tests name `demmesh` and `demmesh_cli` the same way, and `libdemmesh.a` is linked once too.
- `src/mesh/blender_scene.py` is read with `file(READ)` when CMake configures, into the raw string `R"PYSRC(...)PYSRC"` of the generated header. It is listed in `CMAKE_CONFIGURE_DEPENDS`, so the next `cmake --build build` re-runs the configure step after an edit. The configure fails if the script contains `)PYSRC"`, which would end the string early.
- Dependencies are pinned: cpp-httplib v0.46.1 (matches the Homebrew package), ctpl 437e135, CLI11 v2.7.2, Catch2 v3.16.0. Bump cpp-httplib together with the Homebrew package.
- After `brew upgrade` of `openssl@3`, `glfw` or `libtiff`, an existing build tree may still point at Cellar paths that the upgrade removed: delete `build/` and configure again. Never hard-code `/usr/local/Cellar/<formula>/<version>` paths in `CMakeLists.txt`.

## Repository hygiene

`*.tif` and `*.tif.tmp` are ignored, and so are `dem2mesh`'s outputs: `*.stl`, `*.ply` and `*.blend`, the writers' `*.stl.tmp` and `*.ply.tmp`, and Blender's `*.blend1` (a `.blend` has no `.tmp`). The outputs still belong outside the repository. The 20 to 40 MB files in the repository root are download outputs, not sources. Each is RGB16 with the same value in every channel and no georeferencing, and reads as metres = `value * S / 65535`: S is 1100 for `capetown.tif` and its two byte-identical copies (grid and box in `e2bea3e:main.cpp`) and 700 for `simonstown.tif` (`fc7dcef:main.cpp`). In those versions of `main.cpp` the variable `north` holds the southern edge's latitude and `south` the northern edge's. A 0 in these files is not only a negative height: it is also what the old program wrote for a response without `BAND 0:`, for a pixel whose 500 attempts all failed, and for a pixel it never fetched. `new.tif` (1980 x 1645) has no recorded scale or box. Never stage with `git add -A`.
